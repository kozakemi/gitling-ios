# 可恢复的冲突解决流程

## 使用流程

仓库详情顶部会显示正在进行的 merge、rebase 或 cherry-pick；状态页和操作表单也提供“解决冲突”入口。冲突页列出未解决文件，并显示 rebase 的当前步骤和总步骤。

逐个打开冲突文件，可选择共同祖先、当前一方、传入一方查看 Git 索引中的原始版本，也可查看当前工作文件。导入编辑结果后自动切到工作文件预览。删除的一方会明确显示不存在。Rebase 中“当前一方”是新的基底，“传入一方”是正在重放的提交；页面有相应说明。二进制和超过 256 KB 的版本仅显示对象信息，不解压为文本；文本预览最多 80,000 字符。

外部编辑有两种方式：

1. 在“文件”App 或已关联的工作文件夹中直接编辑原文件。
2. 在冲突文件页“准备编辑副本”→“打开编辑副本”，通过系统分享交给编辑器。保存后返回 Gitling，选择“导入编辑结果”。此过程上限为 16 MiB；只导出或分享不会视为已写回。导入会核对冲突版本和导出时原文件的摘要，原文件已有新编辑时拒绝覆盖。

完成编辑后选择“确认解决”，明确确认暂存当前文件。仍包含标准冲突标记时拒绝确认；删除冲突需选择“以删除解决”并确认。修改/删除冲突也可以保留工作文件。所有冲突解决后才允许继续；确认后又编辑了已跟踪文件，必须重新暂存才能继续。Stash 恢复产生的冲突也可使用这个文件解决入口，但不会虚构 merge 操作或删除原 Stash。

“继续操作”完成当前 merge/cherry-pick，或继续 rebase；rebase 后续提交再次冲突时会再次暂停。“中止操作”需明确确认，会恢复操作前分支和已跟踪文件，丢弃解决过程中的编辑，保留无关的未跟踪文件。

## 数据与恢复

- 三种操作开始前要求工作区、索引干净，并处于本地分支；已有修改需先提交或 Stash。
- 保留原生 Git 冲突索引、MERGE_HEAD、CHERRY_PICK_HEAD 或 rebase 元数据。每次进入页面重新从磁盘读取，不依赖内存中的操作对象。
- `.git/gitling-operation.json` 记录本轮操作的原始提交、原始分支和目标。Merge/cherry-pick 先创建提交对象并持久化计划结果，再使用旧 OID 校验更新分支引用，最后清理状态。发布引用前后中断均可恢复，避免重复提交或将已完成提交中止回旧状态。
- Rebase 使用 libgit2 的持久化 rebase 状态重新打开；继续和中止前校验原始分支身份，避免覆盖外部移动后的分支。
- 若文件被替换为目录，或目录被替换为文件，中止前会检查阻挡恢复的内容并拒绝覆盖，用户需先移走；确认删除不会递归移除目录。显式删除符号链接只移除链接本身。
- 普通提交、切换分支、重命名/删除分支、链接/取消链接工作区、Hard Reset 等入口在操作未完成时拒绝执行。普通暂存不能绕过尚未确认的冲突。
- 编辑导入与确认通过文件协调，并沿用仓库写锁；文件协调等待不占用全局 Git 锁。符号链接工作路径被拒绝，避免编辑副本写回到工作区以外。
- 外部工具创建、没有 Gitling 操作记录的操作可以查看/解决文件，但暂不提供继续和中止；应使用原工具完成。这样不会假定未知的操作前工作区是干净的。由 Gitling 启动的操作及其完整复制导入副本可恢复。

## 回归与性能

`ConflictResolutionTests` 覆盖 merge 双父提交、cherry-pick 原作者与说明、连续两个 rebase 冲突及步骤恢复、三种中止、脏工作区拒绝、修改/删除冲突、标记保护、过期导入拒绝、符号链接保护、确认后二次编辑、外部工作区、空 rebase 结果、大型二进制、Stash 冲突、发布引用前后中断、导入暂停中的仓库以及分支被外部移动后的保护。

`AdaptiveLayoutTests` 增加冲突操作按钮在 240～951 点宽度、中/英/日和无障碍字号下的实际 SwiftUI 布局测量。页面长路径换行，版本选择采用菜单，操作组空间不足时纵排。

冲突快照只读取操作记录和索引冲突阶段，不加载提交历史，也不扫描工作文件内容。含 8 MiB 无关文件时，本机初轮 50 次快照查询合计约 28 ms；这是模拟器数据层采样，不是 UI 帧率或真机性能。已有真实仓库分支切换、历史分页、复制导入基准继续离线复用，无需访问服务器。
